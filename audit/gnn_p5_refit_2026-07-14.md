# kubescan — GNN P@5 refit attempt (2026-07-14): summary for deep analysis

## Context

`research/models/checkpoints/` holds the currently-deployed model (commit `f142e1e`,
full Rahman corpus: 599 base graphs / 37 chains / 1154 total). Its GNN cross-validation
P@5 = 0.52 ± 0.098, below the thesis's design target of P@5 > 0.70. An earlier run on a
smaller preliminary corpus (471 graphs / 25 chains) had hit P@5 = 0.72 ± 0.098, so scaling
to the full corpus regressed the primary ranking metric even though classification F1
improved and stabilized. Background on an earlier, unrelated GA-ensemble fix (floor-penalty
regularization solving an escape-only-corner degeneracy) is in `audit/model_fixes.md` —
that fix is unrelated to the P@5 regression investigated here and is already deployed.

## Diagnosis performed (before touching any code)

Inspected `test_results.json`'s `ranked_clusters` and the raw `.npz` graph feature
vectors for the two test chains missed in the deployed model's top-5
(`kubernetes-goof` rank 7, `badpods_priv` rank 8, out of the *old* 91-graph/6-chain
test set). Finding:

- Both rely substantially on `SEC_CONT_OVER_PRIVIL` as an escape signal, which — while
  individually rare across the tabular corpus (4.35% prevalence, comparable to other
  escape flags) — is one of the lowest-importance features in the trained RF model
  (0.32%, because RF's top features are common aggregate flags like `total_misconfigs`,
  `NO_RESO`, not rare per-flag escape signals).
- `badpods_priv` belongs to a 7-member near-duplicate template family
  (`badpods_hostpid`, `badpods_hostipc`, `badpods_hostnetwork`, `badpods_hostpath`,
  `badpods_priv`, `badpods_priv-and-hostpid`, `badpods_everything-allowed` — same
  BadPods fixture, each toggling a different single escape flag). `create_splits.py`'s
  `base_cluster()` only strips the `_aug_NN` augmentation suffix; it has no concept of
  this kind of template family, so the 7 siblings were scattered across train/val/test
  independently. 5 of 7 (driven by `TRUE_HOST_PID`/`TRUE_HOST_NET`/`HOSTPATH_MOUNT`)
  landed in train; the lone `SEC_CONT_OVER_PRIVIL`-only sibling (`badpods_priv`) landed
  in test with no in-distribution training exposure to that specific flag combination.
- Same pattern independently found for a `datadog_*` family (9 members), a
  `simulator_*` family (8 members, mixed isolated/chain), and `kubernetes_goat_*`
  (12 members, mixed clean/isolated/chain, from `research/data/graphs/graph_manifest.csv`).
- Corpus-wide feature-importance check (`research/data/tabular/rf_dataset.csv`, 2827
  rows) confirmed this isn't `SEC_CONT_OVER_PRIVIL`-specific: all individually-rare
  escape flags (`TRUE_HOST_PID` 3.78%, `TRUE_HOST_IPC` 2.16%, `CAP_SYS_ADMIN` 0.71%,
  `CAP_SYS_MODULE` 0.53%, `DOCKERSOCK_PATH` 1.06%) rank low in RF importance (all
  <1.1%) relative to common aggregate features, because tree ensembles need volume to
  reduce impurity and these flags are individually sparse.

## Fixes implemented (commit `14c95e4`, pushed to `feat/completing-thesis-and-comments`)

1. **`research/scripts/05_split/create_splits.py`** — added `family_of()` (groups by
   first `_`-delimited token of the base cluster name) and `group_by_family()`, which
   only treats a family as one atomic leakage unit when it is **label-mixed**
   (prevents scattering chain/non-chain near-duplicates across partitions); label-pure
   fixture families (`checkov_example__*` ×245, `kubeaudit_*` ×114, `gatekeeper_*`
   ×100, `kubehound_*` ×22 — all `isolated`) are left individually splittable so their
   size doesn't distort stratified proportions. Replaced the previous count-based
   allocation (`n_test = round(n * test_frac)`) with a weighted greedy allocator
   (`_greedy_allocate`, largest-weight-first bin-balancing) so each partition's true
   *label* count (not unit count) tracks the requested fraction — a naive first
   attempt at plain family-atomicity (no weighting) produced wildly unstable test-set
   composition across seeds (as few as 3 test chains, ceiling P@5 as low as 0.6, purely
   from which family happened to land in test).
2. **`research/models/train_gnn.py`** — added `FocalLoss` (Lin et al. 2017,
   `--focal-loss` / `--focal-gamma`, default gamma=2.0) as an alternative to the
   existing inverse-frequency-weighted `CrossEntropyLoss`, intended to give
   under-represented *within-class* patterns (not just under-represented classes)
   more gradient. Verified in isolation on CPU: `FocalLoss(gamma=0, alpha=1)` exactly
   matches plain `CrossEntropyLoss` (sanity check), gradients flow correctly.
3. **`Makefile`** — `reproduce` target now passes `--focal-loss` to `train_gnn.py`.

Both changes were bundled into a single retrain (no ablation isolating one from the
other) due to GPU-time cost.

## Open questions for deeper analysis

1. **Is the P@5 drop caused by the split change, the focal loss change, both, or
   neither (i.e. seed variance)?** No ablation isolating the two changes was run.
2. **Why did per-fold CV variance increase so much (σ 0.098→0.271)** despite the split
   fix being specifically designed to produce *more* stable partitions? Working
   hypothesis: forcing whole template families to stay atomic concentrates each fold's
   chain population onto whichever 1-2 families happened to land there (fold 0 got an
   "easy" combination scoring P@5=1.0; fold 1 got a "hard" one scoring P@5=0.2),
   trading leakage-driven optimism for concentration-driven variance — worth checking
   which specific families/graphs are in each fold's val set
   (`research/data/splits/fold_{0..4}_val.txt`) against per-cluster GNN scores.
3. **Is the new, harder test set (5 singleton unseen repos, vs the old scattered
   near-duplicate-heavy test set) revealing genuine generalization limits that were
   previously masked**, rather than the fix making the model worse? The old test set's
   P@5=0.80 may have been partly inflated by chains that were near-duplicates of
   training examples (the very leakage this fix targeted).
4. **Did focal loss help, hurt, or do nothing?** Its interaction with very small
   per-fold batches (some folds validate on only 5-8 chain examples) and the new split's
   higher inherent variance is untested in isolation.
5. **Is `--focal-gamma 2.0` (the Lin et al. default, tuned for dense object detection
   with thousands of examples per class) an appropriate value here** given chain
   examples number in the dozens, not thousands, per fold?
6. Should the split fix be kept (it does fix genuine data leakage / near-duplicate
   test contamination, which is a real methodological problem independent of whether
   P@5 goes up or down), while focal loss is reverted or an ablation run to check its
   individual contribution?

## Deep analysis (2026-07-14, follow-up session)

All findings below come from the existing run artifacts (`/tmp/retrain_results/*.json`,
`research/data/graphs/graph_manifest.csv`, the `.npz` feature vectors, and the split
files regenerated deterministically with seed 42) — no retraining was needed for any
of them. The regenerated split reproduces the retrain's exactly: train 815 / val 88 /
test 86, CV pool 513 originals with 32 chains, matching `ga_weights.json`'s
`oof_n_graphs`/`oof_n_chains`.

### A. Q2 answered: the CV variance is family concentration, not model instability

Per-fold validation chain composition of the new (family-atomic) folds:

| Fold | P@5 | Val chains |
|---|---|---|
| 0 | **1.0** | the entire 8-member `datadog_*` family (near-identical 2–3-node graphs) |
| 1 | **0.2** | the entire 7-member `badpods_*` family (identical 16-node fixture, one flag toggled each) |
| 2 | 0.4 | 6 mixed: 3 `simulator_*` + `emissary`, `kube-prometheus`, `longhorn` |
| 3 | 0.4 | 6 mixed: 2 `kubernetes_goat_*` + 4 singletons (`OpenStack-on-Kubernetes`, `gitcontroller`, `kubernetes-goof`, `kube_security_lab`) |
| 4 | 0.4 | 5 singletons (`CloudFlix`, `aws-ebs-csi-driver`, `datree-tests`, `kube-goat`, `securekubernetes`) |

Because families are now atomic, each fold's P@5 is essentially "how does the model
rank one or two template families it has never seen" — the effective sample size per
fold collapsed from 5–8 chains to 1–3 *families*. σ jumping 0.098 → 0.271 is a
property of the honest split design, not of the model: fold 0 is easy as a unit,
fold 1 is hard as a unit. The working hypothesis in Q2 is confirmed, with the
refinement that it is concentration *by construction* (the family fix working as
intended) rather than unlucky allocation.

Direct corollary: **the old CV 0.52 and new CV 0.48 are not comparable numbers.**
They measure different things (near-duplicate interpolation vs. cross-family
generalization). The drop cannot be read as "the model got worse."

### B. Q3 answered: the old numbers were leakage-inflated

Fold 1 shows it directly: with all 7 badpods siblings held out together, the model
ranks them at P@5 = 0.2; the old split had 5 of 7 badpods in train and the model
"generalized" to the remaining siblings. The same mechanism inflated the old test
P@5 = 0.80. The new fold 1–4 range (0.2–0.4 raw GNN on unseen families/repos) is the
honest generalization estimate under the current corpus.

### C. The GA weight shift is a tie-break artifact; RF contributes nothing to chain ranking

Three independent pieces of evidence:

1. **The GA plateaued instantly**: `ga_results.json` history shows the final best
   objective (0.72) was already present in generation 0 and never improved across
   150 generations. The objective `0.7·P@5 + 0.3·(1−FPR_clean)` is a step function;
   over the OOF pool, vast regions of the weight simplex tie, and the pick inside a
   plateau is arbitrary. On the test set, GA-best (0.517/0.115/0.368) and
   Equal (⅓,⅓,⅓) produce *identical* metrics (P@1=0, P@3=0.33, P@5=0.6).
2. **RF risk is ≈0 for every real-world chain.** From the stored `.npz` feature
   column 25: all 5 test chains ≤ 0.051, all 12 singleton OOF chains ≤ 0.060, and the
   datadog chains are exactly 0.0. Only the synthetic badpods fixtures score
   0.10–0.38. RF's per-manifest risk, averaged over a real repo's mostly-benign
   manifests, dilutes to noise — so `w_rf = 0.517` was fit to a template-heavy OOF
   pool (15/32 chains are datadog+badpods) that the singleton-only test set does not
   resemble.
3. **GNN-only's test P@1 = 1.0 is razor-thin**: top-1 `infra-goof-k8s` at chain-prob
   0.441 vs. false-positive `ansible-hetzner-ubuntu-1804-k8s-setup` at 0.430. The
   P@1 difference between GNN-only and GA-best is one 0.011-wide margin, not a
   robust property of either weighting.

Additional structural finding: the top two ensemble false positives
(`ansible-hetzner…` rank 1, `sa-traefik` rank 2) are **single-node graphs**
(n_nodes=1, escape_cnt=1, escape_fraction=1.0) that the GNN itself scores high
(0.43/0.38). A 1-node graph cannot host a multi-hop attack chain by definition —
a structural prior ("chain requires ≥2 nodes / ≥1 edge") is a legitimate candidate
inference-time fix worth evaluating. Also note the binary escape signal is saturated
in the risky region (every top-12 test graph has escape_signal=1.0; escape-only
scores P@5=0.0) — it separates clean from risky but contributes nothing *within* the
risky region.

### D. Checkpoint selection was misaligned with the primary metric

`train_gnn.py` selected each fold's best epoch by **val macro-F1**, while the
thesis's primary metric is P@5. With family-concentrated folds the two diverge:
fold 0 reached F1 = 1.0 (trivially classifiable datadog graphs) regardless of how it
ranked anything, and the epoch with the best F1 need not be the epoch with the best
ranking. Fixed this session (see F).

1. **`research/models/train_gnn.py`** — new `--select-by {f1,p5}` (`SelectMetric`

**Fix 9 verdict — MRR tie-breaker reverted to 0.0 by default.** Across the three

`--mrr-weight` but disabled by default; re-enable only together with a
family-weighted OOF pool (each template family counting once).

the refit's apparent regression was entirely focal loss, partially masked by the
split fix's honesty gains. Q5 is therefore moot in its premise (γ=2.0 was never
validated here), and the Q6 recommendation is: **keep the split fix, revert

### H. Structural fixes implemented and validated (2026-07-14, follow-up)

**Structural feasibility gate.** A multi-hop attack chain requires reachability
between ≥2 manifests, so a single-node cluster graph cannot host one by
definition. Corpus-verified: all 592 chain graphs have ≥2 nodes and ≥1 edge;
499/537 isolated graphs (and 74/86 test graphs) are single-node — exactly the
population producing the rank-1/2 test false positives. Implemented once in
`kubescan/model/ga_ensemble.py` (`MIN_CHAIN_NODES`, `is_chain_feasible`,
`chain_rank_key`, and an `n_nodes`-gated `predict_label` capping infeasible
clusters at ISOLATED) and consumed by the CLI, `evaluate_test_set.py` (gated
ranking + `ranking_metrics_ungated` for comparison), and `run_ga_ensemble.py`
(weight-independent rank bonus added to all three signal components, which
shifts every convex-combination score by the same constant). Unit-tested.

Validation on the saved ce_f1 fold models (local CPU re-run of GA + test eval):

| Test config (ce_f1 models) | P@1 | P@3 | P@5 |
|---|---|---|---|
| GA-best, ungated (before) | 0.00 | 0.33 | 0.60 |
| GA-best + gate | **1.00** | **1.00** | **0.80** |
| Equal weights + gate | 1.00 | 1.00 | 0.80 |
| **GNN-only + gate** | **1.00** | **1.00** | **1.00 (ceiling)** |
| RF-only + gate | 0.00 | 0.33 | 0.40 |

The gated GNN ranking alone puts all 5 held-out real-world chains in the top 5.
The GA blend keeps the RF-heavy OOF-fit weights (the gated OOF pool has 32
chains among only 84 feasible units, so P@5 plateaus at 1.0 and the weights are
again underdetermined) and gives up one chain (`minik8s-ctf`) at P@5. On this
test set the ensemble adds nothing over the gated GNN — with n=5 chains and a
95% CI of [0.6, 1.0] this shouldn't be over-read, but it belongs in the thesis
discussion of the ensemble's marginal value.

**Family-weighted GA pool: tried, not adopted.** `--pool-agg family` collapses
template families into single pool units (513 graphs → 75 units, 32 → 16
chains). Contrary to the hypothesis in G, the deduplicated pool *still* prefers
RF-heavy weights (w_rf = 0.844) and scores slightly worse on the gated test
(P@3 0.67 vs 1.00 for the graph pool). RF's OOF advantage is not only a
duplication artifact. The option stays implemented behind `--pool-agg` with
default `graph`.
